Attempt 2 merged the writer stop (#130), and Argo scaled `codexctl-0` to zero. The lane driving the cutover ran Codex through codexctl tokens, so it lost its own model access when the server stopped. Nobody could run the backfill, the activation, or the proof, and Amir reverted with #135 (handoff-b33).

## Why Attempt 3 Stopped

On 2026-10-09 the window merged PR W (#166), and `migrate` exited 0. `backfill` then refused with "finish pending logins in file mode before switching storage", although every login journal was terminal. The migrate and backfill Jobs set `fsGroup: 10001` without `fsGroupChangePolicy`, so kubelet added group read and write to every file on `state-codexctl-0` at mount. `vault::private_read` refuses a file with any group or other bit, the renewal journal read failed, and `pending_logins` counts a read failure as pending. The StatefulSet uses `OnRootMismatch` and would not have repaired the modes, so `codexctl-0` could not have read its own state after the revert. The operator restored every mode from the quiesced archive, verified all 8620 paths, and reverted PR W (#171); the token outage lasted about 18 minutes. The Jobs in `central-ha.md` now set `fsGroupChangePolicy: OnRootMismatch`, and steps 3 and the rollback check the modes.

## Canary (Before GO)

The canary runs migrate, backfill, and one real token request on a copy of the file state, before HQ gives GO. It never touches `codexctl-0`, its PVC, the RDS database, or the Ingress, so the expected lane impact is 0 minutes. Run it on the day of the window, at least 3 hours before step 1, so a failure leaves time for a NO-GO.

**The danger is a refresh from the copy.** The copy holds the same OpenAI refresh tokens as the live server. A refresh from the copy rotates the shared grant and revokes every live tab on that account. Older refresh tokens in an old archive may already be spent, and sending one may also harm the live grant. Two facts in the code decide the guard:

- codexctl never sends a refresh itself; every refresh runs inside a `codex app-server` child, which inherits the server environment (`src/central/rpc.rs`, child start).
- On a fresh server the first token request has no fast-path evidence, so it takes the lease path and starts a child (`src/central/fast_path.rs`, `EvidenceMissing`; `src/central/managed.rs`, `ensure_refresh_owner`). The child sends `account/read` with `refreshToken:false`, but Codex can still refresh a stale token on its own.

So the canary removes the network path instead of trusting a setting. Every canary pod that mounts the copy carries the label `app.kubernetes.io/name: codexctl-canary`, and only `NetworkPolicy/codexctl-canary` selects it. That policy allows egress to DNS and to TCP 5432 on the scratch database pod only (`podSelector` `app.kubernetes.io/name: codexctl-canary-pg`), with no `ipBlock`. Do not use the `codexctl-migration` label: its policy allows TCP 5432 to all of `10.1.0.0/16`, which includes the shared RDS database, and a second policy on the same label cannot remove that allow. Canary pods never reference `Secret/codexctl-postgres` or the claim `state-codexctl-0`.

**plat-staging does not enforce NetworkPolicy** (checked 2026-10-11: `aws-eks-nodeagent` runs with `--enable-network-policy=false`, and ConfigMap `amazon-vpc-cni` has `enable-network-policy-controller: "false"`). A pod under the DNS-only policy opened TCP to `auth.openai.com:443`. Keep the policy as an extra layer, but the guard that holds is guard v2, on every canary pod that mounts the copy:

- `dnsPolicy: None` with `dnsConfig.nameservers: ["127.0.0.1"]`, so no host name resolves. Codex reaches OpenAI only by host name.
- `HTTPS_PROXY`, `HTTP_PROXY`, `https_proxy`, and `http_proxy` set to `http://127.0.0.1:9`, with `NO_PROXY=127.0.0.1,localhost`.
- `automountServiceAccountToken: false` and `enableServiceLinks: false`.

A probe pod proves that guard v2 works; it does not prove that a given pod carries it. So check every pod that mounts the copy (the loader, the register pod, both Jobs, and the serve pod) as soon as it runs, before it does any work that can reach Codex: `kubectl get pod <name> -o jsonpath='{.spec.dnsPolicy} {.spec.dnsConfig.nameservers} {.spec.automountServiceAccountToken} {.spec.enableServiceLinks}{range .spec.containers[*]} | {range .env[*]}{.name}={.value} {end}{end}'` must start with `None ["127.0.0.1"] false false`, and each `|` section (one per container) must contain all five of `HTTPS_PROXY=http://127.0.0.1:9`, `HTTP_PROXY=http://127.0.0.1:9`, `https_proxy=http://127.0.0.1:9`, `http_proxy=http://127.0.0.1:9`, and `NO_PROXY=127.0.0.1,localhost`. In addition, for pods from the window image, `kubectl exec <name> -- node -e 'fetch("https://auth.openai.com").then(()=>console.log("OPEN"),e=>console.log(e.cause&&e.cause.code))'` must print `EAI_AGAIN`. A Job pod finishes on its own, so create each Job with `spec.suspend: true`, run the same `jsonpath` check on the Job with `.spec.template.spec` in place of `.spec`, and only then set `spec.suspend: false`. If any check fails, delete the pod and stop.

With no resolver, canary pods reach the scratch database by the Service ClusterIP, not by name. Nothing blocks TCP to the RDS address; the guard against RDS is that no canary pod references `Secret/codexctl-postgres`.

Never send the canary token request with `codexctl central-token`. That command requests billing evidence and sends `previousRevision` for near-expiry tokens; the server honors forced requests only for near/unknown expiry, subject to the rotation guard. Use the direct HTTP request below without either field to make the no-refresh canary contract explicit.

All canary objects are in namespace `codexctl` with names that start with `codexctl-canary-`, so the copy and the vault key never leave the cluster.

1. **Scratch database and policy.** Start pod `codexctl-canary-pg` (`postgres:16`, label `app.kubernetes.io/name: codexctl-canary-pg`, `emptyDir` data) and a ClusterIP `Service/codexctl-canary-pg` that selects that label on port 5432. Create `Secret/codexctl-canary-db` with the keys that the Jobs read from `Secret/codexctl-postgres`: `db-hostname` = the ClusterIP of `Service/codexctl-canary-pg` (read it with `kubectl -n codexctl get svc codexctl-canary-pg`), `db-port` = `5432`, `db-name`, `db-user`, and a random `db-password` that matches the scratch pod. Create `NetworkPolicy/codexctl-canary` as described above. Run `kubectl -n codexctl get networkpolicy -o yaml` and confirm that no other policy selects the `codexctl-canary` label.
2. **Scratch claim.** Create PVC `codexctl-canary-state` with access mode `ReadWriteOncePod`. Only one pod mounts it at a time: delete each claim pod (loader, register, Jobs, serve) and wait until it is gone before the next one starts. A loader pod (image busybox as in the attempt 3 backup reader, label `codexctl-canary`, user and group 10001, no `fsGroup`) receives the archive with `kubectl cp` and unpacks it into `/data/state` with `tar -xpzf`, which keeps the modes. ### H owns the final handoff (Operator binding, 2026-10-12)

H must not inherit its only writer-stop fence from W: W can be reverted before H is merged. H renders `StatefulSet/codexctl` at zero through its own `writer-stop-patch.yaml`, independently of W's top-level replica transform. Reverting W's block therefore cannot remove H's fence. Argo applies the writer and dependencies in wave 0, the ordinary `Job/codexctl-final-backfill-a5` in wave 1, and `Deployment/codexctl-ha` in wave 2. The ReadWriteOncePod claim prevents the final Job from mounting alongside the old writer. Job completion gates HA creation; failure or its 1800-second deadline stops the sync before HA. That bounded budget includes the file writer's 600-second termination grace, PVC scheduling and backfill; Job Pending time counts toward it. Never selectively sync the HA Deployment or skip the Job/wave gates.

This repeats section 5's final backfill even after W's initial migrate/backfill. Freeze the final Job's full image reference so later account-server image pins do not alter its immutable pod template. Keep the completed Job without a TTL and without a Sync hook: later syncs must not replay file backfill against a live HA store. A new attempt needs HQ review, a new Job name, and the same no-writer prerequisites. Do not delete the final Job while HA is running. H's `spec.replicas: 0` patch stays in Git through I and until reviewed cleanup.

Before H, W still provides the quiesced archive, private-mode baseline, initial migration and backfill receipts. The mode checks and `fsGroupChangePolicy: OnRootMismatch` remain mandatory. After H, preserve the final Job log. Its JSON reports inserted/updated rows, not database totals: after the successful initial backfill with no intervening writer, the final pass normally reports zero changes. Separately run the read-only row-count Job and compare live users/accounts/devices totals with the initial receipt and stopped source inventory. Unexpected changes, errors, or total mismatches stop I and go to HQ. The immutable image is unchanged. Approval and green checks do not authorize merging H: a merge auto-deploys staging.

### Staging database reset: prepare only

`deploy/k8s/jobs/b33-reset-data.yaml` is a standalone, destructive Job, excluded from every Kustomization. Do not run it without a separate HQ GO naming the staging database and retained backup. Before an authorized run, stop every PostgreSQL writer, confirm no HA pods or credential/login workers remain, settle every lease, and retain database/PVC receipts. It refuses an unexpected table inventory, a schema other than layout 8, an unreleased lease, or a live login holder. It truncates only the fixed codexctl data-table set in one transaction, without CASCADE, preserving `central_schema_migrations` and `central_identity_migration_progress`. It prints names/counts only. A different schema (including dashboard tables) needs a newly reviewed reset Job. After an authorized reset, run the read-only count Job: every data table must be zero; only the two metadata tables are exempt, and their counts and rows must match the pre-reset receipt. Do not interpret its generic pre-migration "every table zero" comment as the reset gate. Then retain fresh initial migrate/backfill receipts; never reset an HA store to repair a live request.

PR H must not remove `PrometheusRule/codexctl` or `ScrapeConfig/codexctl`: the staging-ha overlay lacks both, and prune would delete them. To cut the Argo poll delay (about five minutes on 2026-10-07), the operator may request a refresh with `kubectl -n argocd annotate application codexctl argocd.argoproj.io/refresh=normal --overwrite`.

## Rollback

- **Before PR H (steps 3 to 5):** revert PR W. `codexctl-0` returns on the same PVC and the file state is still authoritative. This is the attempt-2 rollback. If any Job or pod mounted the claim after the step 3 baseline, first compare every path's mode, owner, and group with the baseline through a read-only pod. The claim is ReadWriteOncePod, so only one pod can mount it at a time: delete each pod and wait until it is gone before the next one starts. If any line differs, delete the read-only pod, then restore the baseline group and mode of each differing path with a pod that runs as user and group 10001, mounts the claim writable, and sets no `fsGroup`. Set the group first (`chgrp`), then the mode (`chmod`), because a group change clears the setgid bit. That pod can set only group 10001 on files that user 10001 owns. So before the restore, check each differing path: its current owner and its baseline owner must both be 10001, and its baseline group must be 10001. If any path fails that check, stop and ask HQ, and do not revert PR W. Delete that pod, compare again with a new read-only pod, delete it, and revert PR W only after every path matches. `codexctl-0` cannot read a secret file that has a group or other bit.
- **After PR H:** fence the HA writers before the file writer returns, in this order:
  1. Revert PR I if merged. `Service/codexctl` has no endpoints, so token traffic stops.
  2. Merge a reviewed rollback revision that sets `Deployment/codexctl-ha` to zero while retaining H's `StatefulSet/codexctl` zero and completed final Job. Wait until no `codexctl-ha` pod exists (`kubectl -n codexctl get pods` shows none; the pods have a 60-second grace period). Do not directly revert H: removing its zero-replica fence could restart the file writer before HA has exited.
  3. Run the read-only [lease check](#read-only-queries) with `kubectl -n codexctl create -f deploy/k8s/jobs/b33-check-leases.yaml`; it counts unreleased leases only. Every `account_refresh_leases` row must be released, including login leases (holder `<login holder>:<operation id>`). An unreleased row, even an expired one, means the owner's settlement is unknown: stop, keep PR W merged, and forward-fix in HA. A login operation may hold a grant that file mode cannot see, and the operator has no per-user authority to read the login journal. So settle open logins in HA first: ask the affected users to finish or cancel them through their own sessions.
  4. After the lease and private-mode checks pass and affected credentials are reconciled, HQ may approve removal of HA resources and the completed Job while preserving writer zero. Only then approve a separate revision restoring the file writer. That final revision must remove H's writer-stop patch and, if W's top-level zero-replica transform is still present, remove it too (by reverting W or an explicitly reviewed equivalent). Reverting W alone cannot restore the writer because H owns an independent fence. Never combine HA termination and file-writer restoration in one sync.
- **Spent tokens:** if the HA logs show any refresh, the file state holds a spent refresh token for each refreshed account. Each such account needs `codexctl login <alias>` and a device code approved as in prerequisite 5 before it serves in file mode. Prefer a forward fix in HA when the fault allows it.
- **HA-only credentials:** after PR H, assume that some account was added or renewed through HA (PR2 add-account, PR1 renewal) or holds a captured candidate, so its credential exists only in PostgreSQL. The operator does not read the login journal across users. A forward fix in HA is the preferred path. If file mode must return, every user compares `codexctl list` with their expected accounts and re-adds or runs `codexctl login <alias>` through their own authorized session before their lanes resume.
- Never run the StatefulSet and the HA Deployment as refresh writers at the same time. Keep the PVC archive, both Job logs, and the database until HQ closes B33.

## Read-Only Queries

No `codexctl-central` command reports row counts or lease state, so the operator runs them as one-shot Jobs (`deploy/k8s/jobs/b33-check-empty.yaml` before migration, `deploy/k8s/jobs/b33-check-leases.yaml` in a rollback) with a `postgres:16` image, the `codexctl-migration` label (for the egress policy), the `codexctl-postgres` Secret as `PG*` environment variables, and `PGOPTIONS=-c default_transaction_read_only=on`. The Jobs are reviewed and merged before the window; no kustomization includes them.

```sql
-- Emptiness (prerequisite 3): exact row count of every table that exists.
-- No output row, or 0 in every row, means empty.
SELECT table_name,
       (xpath('/row/c/text()',
              query_to_xml(format('SELECT count(*) AS c FROM %I.%I', table_schema, table_name),
                           false, true, '')))[1]::text::bigint AS row_count
FROM information_schema.tables
WHERE table_schema = current_schema() AND table_type = 'BASE TABLE'
ORDER BY table_name;

-- Lease fence (rollback step 3): must return 0.
SELECT count(*) FROM account_refresh_leases WHERE NOT released;
```

The emptiness query names no table, so it also works before migration 1, when no table exists, and it counts tables added later, such as the loan tables. The lease query runs only after migration, when its table exists. No query reads the login journal across users.
